## Required D1 procedure (proposal, not owner acceptance)

1. Record separate, time-bounded, single-account, owner-authorized case; protect the opaque authorization ID from application and web roles. Authenticated Lemon Squeezy per-account/checkout/invoice/order read and quiet period are external prerequisites. A local SQL clearance row is **not** proof of cessation.
2. Inside one SQL transaction and account profile lock, check active case, approved pre-Auth provider evidence, all local billing holds, open privacy requests and deleted-profile state. Execute **only that account's** Phase A; no due-account scan, batch Phase A or implicit cron.
3. Reclaim a single-account Auth lease under the account lock. Record the irrevocable Auth-attempt intent *before* HTTP. Recheck the local fence and authorization. A previous/unknown attempt requires fresh Admin GET and owner reconciliation, not blind repeat DELETE.
4. Only the owner-supervised operator may send Auth DELETE, and must independently verify authenticated Auth GET. Unknown GET, timeout, mismatched user, expired lease, signed new payment or uncertain response creates a durable financial/identity hold and no completion.
5. After verified Auth retirement, **stop**. Do not confirm release, enqueue a dispatchable completed email, close privacy requests or discard the minimal recovery email. Owner must re-read paginated merchant subscriptions/invoices/orders/checkouts and reconcile signed receipts/settlements **after Auth retirement**.
6. Owner records a distinct post-Auth clearance bound to the account, case and Auth observation. The DB barrier must check the clearance time and every newer signed incident under the account lock. Then, and only then, permit a staged nondispatchable email and an atomic release of email, privacy-request status and custody.
7. Any subsequent unknown, retried or late signed charge invalidates the clearance and creates a durable incident. Never restore a retired Auth identity or benefits automatically. Owner handles merchant refund/remediation, communication, legal/privacy deadline and monitored incident recovery; a fresh verified provider clearance and a **new** explicit supervised authorization are necessary before retry.

## 2026-11-10 continued author implementation — still isolated and uninstalled

The initial 423 containment in #1230 now has a **separate, uninstalled SQL review overlay** at `supabase/tests/research-p1/a-strict-overlay-review.sql` and an **unrouted, synthetic-only** JS orchestration module at `apps/web/src/lib/account-deletion-a-strict-review.js`. The executable matrix is `supabase/tests/research-p1/test_a_strict_review.py` plus `apps/web/scripts/test-account-deletion-a-strict-review.mjs`.

SQL owner custody: `a_strict_authorize` is postgres-owner-only (not service_role) and issues one opaque, expiring, single-account authorization after owner-recorded pre-Auth clearance. `a_strict_owner_rotate` is also owner-only, invalidates the old capability, preserves the prior Auth attempt and refuses active leases/unresolved incidents. SQL `a_strict_phase_a`, `a_strict_claim`, `a_strict_fence` and `a_strict_mark_auth_attempt` guard the one-account path. No second Auth-attempt intent can be created. The owner must independently verify the actual Auth Admin GET; the SQL `a_strict_record_auth_observed` stores an operator attestation, not direct Auth evidence.

After Auth is retired, SQL requires a distinct owner-recorded, **post-Auth** merchant clearance. The owner-only `a_strict_owner_post_auth_clearance` requires the case, the post-Auth verified_at timestamp and attestations covering paginated provider evidence, invoices and future billability. The provider API itself is never called by this code. Both `a_strict_confirm_release` and `a_strict_finish_release` recheck the private post-Auth barrier under a profile lock. Existing outbox triggers continue to stage an email as nondispatchable until the final SQL acknowledgement. A signed paid event creates a durable incident and blocks release; `a_strict_hold` can only tighten hold custody and does not restore Auth, access or financial rights.

A successful owner attestation is **not** cryptographic proof that Lemon Squeezy stopped charging, and neither the SQL lock nor a short freshness rule makes merchant and Auth operations atomic. The schema still lacks an independently verified trusted owner-signature mechanism; private case/capability custody is a proposed design, not D1 approval. **D3 15-minute clearance from #1229 was NOT incorporated**; the historical 24-hour rule remains solely as a reference for owner policy review.
