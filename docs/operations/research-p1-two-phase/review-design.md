## Verified source constraints

* `public.finalize_account_deletion(uuid)` requires `profiles.auth_user_id IS NULL`. A direct Auth↔SQL swap is wrong.
* An existing `public.prepare_account_deletion_auth_removal(uuid)` detaches the nullable foreign-key link inside a SQL transaction; it **does not call Auth Admin**.
* The old app uses three independent steps: readiness RPC → Auth DELETE → SQL finalization. A new signed payment between the first two can leave a deleted Auth identity and a billing-held database profile.
* The SQL owner clearance is not evidence that Lemon Squeezy stopped billing by itself. The owner must authenticate external merchant state. `cancel_scheduled`, `past_due`, local `cancelled`, and a locally forged `provider_webhook` row are **not** proof of settled billing.

## D2-43 — Follow-up on Claude F1–F5 (Draft-only, 2026-11-06)

* **F1 — Durable nonactive signed facts:** Authenticated, bound Research renewal/resume events on `deletion_pending` or `deleted` are recorded as `held_nonactive` receipts with their original requested target state. No subscription or entitlement grant is applied. The same signed event key is idempotent; replay compares original signed fingerprints. A newly persisted event invalidates older merchant attestations.
* **F2 — Incident custody:** Two narrowly scoped triggers record a private incident in the same SQL transaction when a new signed bound event or paid-binding quarantine delivery targets a previously database-finalized account. The incident has an opaque account key, event types, observation times and a durable count; it sets a recoverable last-error code, opens a financial hold and blocks Auth confirmation, email release and privacy completion. An owner-only resolution function requires a **fresh** provider clearance later than the incident and a case reference, and cannot be called by web/API roles. Signed quarantine history remains a financial footprint after `resolved_at` changes; simply editing that field or recording a new clearance cannot automatically release incident custody.
* **F4 — Bounded request and lease scope:** The Draft worker bounds SQL/Auth and staged-outbox HTTP requests with a 25-second abort signal. The runnable cleanup batch is one account only; raw lease capability in SQL remains administrative. Aborting a client request does **not** establish that the server canceled it. Leases, status rechecks and outbox deduplication remain required.
* **F5 — Privacy request preservation:** Phase A refuses to detach account identity if any non-deletion privacy request is still `open` or `in_progress`; the accountable privacy owner must handle it before account deletion proceeds. A terminal non-deletion request can be pseudonymized with the rest of the account.
* **Unresolved hard P0:** A signed payment can still commit between the SQL billing fence and irreversible Auth HTTP. Durable incident custody improves audit and conditional recovery, but **cannot undo an already deleted Auth identity**, guarantee cancellation at Lemon Squeezy, or constitute refund/notification authority. The expected-defect witness is intentionally part of CI but is **not** evidence of billing safety.
* **Hosted release blockers:** actual Development UI02/UI03 and shared outbox trigger/constraint parity, Auth GET/DELETE/JWT/refresh behavior, legacy worker drain/rollback, verified per-target merchant cessation, owner-approved financial restitution/privacy SLA and separate owner acceptance remain HOLD. ## Candidate phase protocol

1. **Phase A: atomic DB commit (pre-Auth).** In one database transaction: lock the canonical profile `FOR UPDATE`; enforce status/deletion due; evaluate *all* known billing evidence, open checkouts and unresolved signed-payment quarantine; require a current owner-recorded externally verified cessation for every Research footprint; capture pending privacy-request IDs and the necessary recipient email in a private RLS-forced custody row; call the existing auth-link detachment helper; invoke the existing SQL finalizer; then revert privacy-request status to `in_progress` until later confirmed Auth retirement. If any statement fails, the entire SQL transaction rolls back—**zero Auth DELETE calls**.
2. **Phase B: leased Auth cleanup.** A bounded `service_role`-only RPC leases incomplete rows with `FOR UPDATE SKIP LOCKED`, fresh opaque lease IDs and a 15-minute retry interval. The review-only web module requires canonical Development config. For `auth_pending`, request Auth soft deletion and independently query Auth Admin: only 404 or a matching identity with valid `deleted_at` is accepted. Unavailable/malformed/active responses **hold**; nothing is marked complete. The original recipient email stays in the inaccessible private custody ledger.
3. **Phase C: staged email and atomic acknowledgment.** Confirm the current Auth lease in SQL after verified Auth retirement. The existing idempotent completion-email helper inserts an outbox record, but the Draft Part 10 trigger forces it to non-dispatchable `deletion_staged` after checking Auth custody and billing evidence. The SQL finisher, under profile/private/outbox locks, rechecks billing and atomically marks private custody `email_enqueued`, changes outbox status to `queued`, scrubs temporary recipient-email custody and completes the recorded privacy requests. A service-role direct PATCH cannot release the staged message before the private phase commits.
4. **Recovery:** Crash before Phase A commit → SQL rollback, Auth untouched. Crash after A commit → durable Auth queue survives. Auth DELETE 503/network timeout → retry lease after 15 minutes. Auth returns 404 on repeat → verify absent and resume. Crash after Auth DELETE before SQL acknowledgment → repeated Auth check, re-leased token. Crash after Auth confirmation before email → skip Auth deletion and retry idempotent enqueue. Crash after email enqueue before SQL acknowledgment → outbox deduplication and SQL completion on retry. Lost/expired leases cannot confirm. Concurrent claims skip locked rows.
5. **Paid event ordering:** checkout creation/binding and lifecycle transitions already lock the profile; the Draft quarantine writer now also takes a profile `FOR SHARE` lock before writing verified payment evidence. Thus an event that commits **before** Phase A prevents irreversible database deletion. An event arriving after Phase A must still be saved as financial quarantine (never silently dropped or regranting benefits), trigger incident/support reconciliation and not be treated as proof of successful account billing cessation. External merchant certainty remains an owner-specified release prerequisite.

The new SQL is in `supabase/migrations/20261105190000_research_p1_billing_safe_lifecycle.sql` as **Draft Parts 9–10**, and the review-only, unregistered JS module is `apps/web/src/lib/account-deletion-two-phase-review.js`. They are intentionally **not called** by `api/account` or the deployed cron. Their tests run in GitHub Actions with synthetic identities and a disposable PostgreSQL 17.6 database only.

## Additional Draft billing and worker lease hardening (2026-11-05)

* **Expired checkout != no charge.** All issued checkout attempts remain durable billing footprints even after their `hold_until` window has passed. A still-open window is an absolute hold; after expiry, the attempt still requires owner-verified external merchant reconciliation observed **after** its latest mutation. A failed attachment remains observable.
* **Evidence time != entry time.** Only `research_billing_clearances.verified_at` can be used to establish that external merchant verification followed the latest local financial footprint. `recorded_at` is audit metadata, not a substitute for checking the provider. Future-dated verification, including a one-minute offset, is rejected. Neither SQL time check proves an external observation actually occurred: owner evidence custody remains mandatory.
* **Lease expiry is authoritative.** `confirm_deletion_auth_cleanup` and `finish_deletion_auth_cleanup` reject a worker when `next_attempt_at` has expired, even before a second worker reclaims that row. Claim tokens never authorize acknowledgements indefinitely.
* **Safety caveat:** The currently deployed finalizer still invokes the old Auth-first chain, and older privileged RPCs have not been cut over or contained. These modifications are Draft migration/test changes only; no real merchant cancellation/expiry semantics, hosted Auth behavior, or Production compatibility has been validated.

## Late-payment fence and isolated full-cycle candidate (2026-11-05)

* A new `service_role`-restricted `check_deletion_auth_cleanup_billing_fence(uuid,uuid)` verifies a current lease, finalized database identity and **zero presently observed new Research billing holds** under the same profile lock used by signed paid-binding evidence. The unregistered JS review module checks it before any Auth Admin operation.
* `confirm_deletion_auth_cleanup` and `finish_deletion_auth_cleanup` now acquire the profile lock **before** the private cleanup row (the Phase A lock order), repeat billing reconciliation, and block new signed payment evidence from being silently treated as deletion completion. Expired leases cannot bypass the checks. Both steps preserve a retryable queue on refusal.
* `runDraftTwoPhaseReviewCycle` combines the bounded/fair due scan, transactional Phase A and leased Auth recovery **only inside the existing unregistered, Development-ref-only review module**. Invalid or duplicated due-account receipts fail closed, and a failed Phase A is never followed by an Auth DELETE for that identity.

A security-definer INSERT trigger validates the Auth-confirmed private queue, exact recipient and state version, and no observed new billing; the SQL finisher transitions to `queued` only in the same transaction as privacy completion and private queue scrubbing. The global outbox status constraint/trigger is a **shared-schema change needing separate impact review**.

Genuine merchant cessation, hosted Auth Admin response semantics, legacy API path/grants cutover, dispatch-worker behavior on `deletion_staged`, and independent migration/privilege review are not verified. ## Lemon Squeezy provider-evidence review procedure (proposal; no merchant calls performed)

The API references below are **documentation**, not an authenticated account inspection or proof that any particular subscription stopped. A paid customer and all product/provider identifiers remain private.

1. **Custody/identity.** Starting with signed Research purchase and webhook/checkout records, match canonical merchant `store_id`, `product_id`, `variant_id`, `order_id`, `subscription_id`, `customer_id` and checkout ID. Do not infer "no subscriptions" from an empty USD Impact `subscriptions` table or email-only lookup. Resolve mismatched or missing identifiers before release.
2. **Read-only merchant enumeration.** From an owner-authorized session, use `GET /v1/subscriptions` with documented `filter[store_id]`, `filter[product_id]`, `filter[order_id]`, `filter[variant_id]` and, where appropriate, `filter[user_email]`; follow **all pagination links**. Verify each relevant ID using `GET /v1/subscriptions/:id`. Cross-check subscription invoices and related orders, provider-native charges/retries, and pending/refunded payment incidents. No token or customer payload goes into CI or the code repository.
3. **Actual renewal/cancellation state.** Per Lemon Squeezy documentation, `past_due` can retry up to **four times over two weeks**; `unpaid` can remain in dunning; `paused` is not permanent cancellation. `cancelled` means future payments cancelled but subscription may remain in paid grace period and **can be resumed**; it is not the same state as `expired`. Verify that remaining scheduled renewals, retries, provider actions and resumption paths are resolved before owner attestation.
4. **Checkout window.** For every issued checkout, read its exact `GET /v1/checkouts/:id` object. `expires_at` may be `null` (perpetual); a dated checkout expires for **new checkout purchases** but does not exclude already initiated payments, pending settlement, or delayed signed delivery. Only an owner/provider-confirmed charge-path reconciliation can clear a persisted attempt after expiry.
5. **Attestation.** Preserve provider-native response/request timestamp, scoped IDs, read-only authenticated audit receipt and conclusion in protected owner custody. Record an opaque reference, `verified_at` (actual provider observation, never row entry time), source and owner through the owner-only clearance writer. Reject missing invoices, uncertain retries, unresolved paid-but-unbound cases, missing charge-path enumeration and stale confirmation. Provider support confirmation may be needed.
6. **Late event and privacy escalation.** If a signed charge arrives **after** Phase A, retain financial quarantine, interrupt the Auth/email completion fence, and open an owner-controlled billing/privacy reconciliation incident. An already retired Auth identity cannot be undone. Do not silently auto-refund, fabricate a cancellation webhook, clear holds on a timer, or send the completion acknowledgment while incident status is ambiguous. Owner must approve the maximum privacy hold/SLA and any payment remedy.

Official API references: [List subscriptions](https://docs.lemonsqueezy.com/api/subscriptions/list-all-subscriptions); [Subscription states](https://docs.lemonsqueezy.com/api/subscriptions/the-subscription-object); [Managing subscriptions](https://docs.lemonsqueezy.com/guides/developer-guide/managing-subscriptions); [Retrieve checkout](https://docs.lemonsqueezy.com/api/checkouts/retrieve-checkout); [Checkout expiry](https://docs.lemonsqueezy.com/guides/developer-guide/taking-payments); [Subscription invoices](https://docs.lemonsqueezy.com/api/subscription-invoices/list-all-subscription-invoices).
